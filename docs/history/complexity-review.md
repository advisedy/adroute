# 项目复杂度与简化建议

本次在完成“模型对外开放状态”和“网页默认模型”分离后，对现有实现作了只读评估。以下是建议，不代表已经删除或重构这些功能。

## 总体判断

AdRoute 已不只是一个 HTTP 转发器，还承担客户端配置管理、后台进程管理、上游异常响应修复、诊断资料交接和安装配置。主要复杂度来自这些产品承诺，而不是 Go 本身。此前迁移选择保留完整功能，也保留了这些维护成本。

我认为可以做减法，但应减少不常用的功能承诺，而不是删掉保护用户配置和凭据的检查。

## 最值得关注的地方

### 1. 自动修改客户端配置：收益很大，维护成本也最高

`internal/adroute/codex_config.go` 不仅写一个地址，还要处理 TOML 的 profile、引号、内联表、注释、备份、所有权与后续用户修改，并支持恢复。`internal/adroute/opencode_sync.go` 对另一种 JSONC 格式维护类似的安全写入约束。

这些不是同一功能的简单重复，但对于本机工具，承诺同时无损维护两种客户端配置确实偏重。

建议：保留当前行为，先确认 OpenCode 自动同步是否经常使用。如果很少用，未来可考虑只提供手动配置说明；Codex 自动接入也可以评估是否需要从每次启动中拆成明确的接入操作。代价是少一些自动化便利。**本次没有改变这些已承诺的行为。**

### 2. 兼容修复与诊断：真正复杂，但不能笼统判成多余

`compatibility.go`、`adapter_stream.go`、`adapter_channels.go`、`adapter_snapshots.go` 负责工具调用身份、参数片段、最终快照与正文边界；`diagnostics.go` 和目录管理又提供采集、授权、脱敏、回放与交给本地 AI 的资料路径。

对于确实遇到异常上游的用户，修复算法有实际价值。更值得质疑的是是否需要把全部包管理、版本管理、原始诊断导出和交接都放在日常主流程中。

建议：先在现有包内把格式验证、修复算法、包存储等职责拆成更聚焦的文件，并把低频诊断放在高级入口。若未来不再使用原始诊断交接，可以连同其界面和契约一起缩减；不能一边保留导出，一边删除隐私保护。

这里的 v1/v2/v3 是协议修复能力版本，不是已移除的旧配置迁移，不应因为名字带版本就删除。

### 3. 页面状态与部分保存：存在可避免的复杂性

`public/controller.js` 同时维护多个弹窗、未保存草稿、异步请求、版本戳和登录会话。取消、关闭弹窗、退出登录和延迟响应都必须配合，否则容易显示错误状态或恢复敏感信息。

本次最明显的问题是“启用路由”同时让人联想到开放模型和选择默认。现在已经拆清楚：保存配置不等于设为默认；开放状态决定外部能否看到和调用；默认只是开放条目中的一个选择。

另外，本次联调曾出现“前端先保存 Key，再另发请求关闭默认模型”的补救方案。我不建议保留这种绕路：两步可能部分成功。最终已改为后端在一次保存中完成状态和默认值的原子更新。

后续可以逐步把各表单的草稿和请求状态收拢为局部控制器，但不建议为此立即换前端框架，也不应再把开放开关拆成多层相互覆盖的状态（当前只有逐条目的一层开放状态）。

### 4. 文件安全逻辑重复、部分文件过大：适合局部整理，不适合再次重写

Store、Codex 配置、OpenCode 同步和安装器都包含安全文件读写、备份和并发复核。部分语义确实重复，但配置格式、恢复范围和生命周期不同，不能为了复用而强行共用一个巨型事务框架。

建议：先拆清 `codex_config.go`、`compatibility.go` 和 `cmd/adroute/main.go` 中的职责；只有在重复逻辑和测试语义确实一致时，才抽取少量窄的文件操作函数。暂时保留单个 `internal/adroute` 包，不创建多层 repository/service/usecase 包装。

### 5. 一键安装与 PATH：方便用户，但不是“复制一个文件”那么简单

`install.sh` 的主要成本来自持久修改 Bash/Zsh 启动文件，而非编译。用户明确需要一次安装后长期使用命令，因此这部分便利有价值；相应的备份、标记块校验、确认和重复执行保护不能省。

如果未来要极简安装器，正确做法是放弃自动改 Shell 文件，接受手动配置 PATH 的体验成本，而不是保留自动改写却删除保护。**当前没有建议回退这次已经做好的安装体验。**

## 我建议的下一步顺序

1. 先整理最大的几个文件和弹窗状态，不改对外行为，也不引入新框架。
2. 根据真实使用情况，评估 OpenCode 自动同步、原始诊断资料交接等外围功能是否值得长期维护。
3. 保持模型开放状态只有一层；不要引入“当前 Key”、自动轮换、故障换模型等隐式机制。

## 不建议为了减代码而删掉的内容

- 管理令牌与代理令牌分离、Host/Origin 检查、私有文件权限。
- 每个条目固定自己的上游连接，未知、删除或关闭的模型明确拒绝，不自动替换。
- 请求到达时固定路由快照、流式取消、超时、内存上限和工具身份校验。
- 修改用户配置前的备份、可检测并发修改的拒绝，以及恢复时保留后来编辑的约束。
- 修改启动文件前的明确确认，以及诊断采集和分享的隐私确认。

减少这些检查只会把显式代码复杂度变成数据损坏、凭据泄露或错误调用的风险，不是可靠的简化。
